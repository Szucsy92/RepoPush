# AGENTS
- Client-only Vite + React SPA, no server or router: everything ships as static files so it runs on GitHub Pages under any sub-path (`base: "./"`).
- GitHub access goes through the `GitHub` class in src/lib/github.ts, which takes the user's token explicitly and refuses any origin other than api.github.com; the CSP connect-src enforces the same.
- Commits use the Git Data API (blobs→tree→commit→force ref update) so ZIP replace/merge and patches are single atomic commits; destructive runs show a change-plan confirmation computed from git blob shas first. Existing files keep their git mode (executable bit, symlink) through `getTree().modes` → `FileOp.mode`; only new files get the name-based guess (`*.sh`, `bin/`).
- ZIP parsing and patch application run in the browser (src/lib/repo-files.ts).
- The Android APK is built by .github/workflows/android.yml: Capacitor shell generated in CI (`cap add android`; the only committed Android sources are native/BiometricVaultPlugin.java, native/PressHapticsPlugin.java, native/SystemInsetsPlugin.java and native/AppIconPlugin.java (plus the icon resources in native/res), copied in), signed with a keystore generated once and stored AES-encrypted on the `signing` branch (password in the ANDROID_KEYSTORE_PASSWORD secret). The app detects the shell via src/lib/native.ts (no service worker, log copy instead of blob download).
- Service worker is generated by vite-plugin-pwa and registered only from src/lib/pwa.ts, which refuses dev and iframes.
- A remembered token is never stored as plain text: src/lib/lock.ts keeps it as an AES-GCM vault keyed from a 6-digit PIN (PBKDF2), with a wrong-PIN counter (wipe after 10). Biometrics (Android shell only) use the in-repo Capacitor plugin native/BiometricVaultPlugin.java (Keystore key behind BiometricPrompt, copied into the generated project by the android.yml workflow) to keep the PIN behind the fingerprint. Session-only tokens (no "remember") skip the PIN.
- UI: surfaces are matte frosted glass (translucent --card/--popover plus backdrop blur in styles.css), the corner radius comes from --radius, and every press gets a visual (scale) and haptic tick from src/lib/haptics.ts (data-haptic="medium" marks main actions).
- The Android app is edge-to-edge: status/navigation bars are transparent and the layout pads itself with --inset-* CSS variables (class app-insets / pad-inset) fed by the SystemInsets plugin via src/lib/insets.ts.
- Colour themes (easter egg): double-tap the RepoPush brand to cycle default → coral → sky → sun → violet. src/lib/theme.ts sets [data-theme] on <html> (CSS variables in styles.css: --primary, --brand, background hues), and the Android launcher icon follows via activity-aliases + the AppIcon plugin when the app goes to the background. Success/added colours use --ok (always green). If a theme colour changes, change it in styles.css (--brand) and in native/res/drawable/repopush_fg_*.xml.
- Build tracking is per repo: src/lib/build-track.ts keeps one `Track` (runs, building, stopping, …) and its log lines per repo, and App.tsx runs one poller per repo (`startTracking`), also in the background when another repo is open. The Build/Stop button, status strip and log only read the open repo's track, so a build in repo A never blocks starting one in repo B.
- Build notifications: the bell in the header lists (1) one live row per repo whose build is running or queued (`liveNotes` in src/lib/notes.ts, derived from the tracked runs and, for the open repo, the watcher's runs; runs with a stop request do not count; it is never stored and a closed bubble does not remove it) and (2) a `Note` for every finished build, labelled with repo and time. Finished notes come from the build poller (any repo, also in the background) and from the open repo's watcher (pushes, other machines); `notify` in App.tsx sends one note per run id, so a run seen by both is reported once. The bubble scrolls when there are many; tapping a row opens that repo; closing the bubble discards the finished notes only.
- In-app update (OTA, Android only): src/lib/ota.ts looks up the latest release of VITE_RELEASE_REPOSITORY through api.github.com (the CSP stays untouched), compares the number at the end of the tag (v1.0.<run number>) with the installed versionCode, and src/UpdateDialog.tsx offers it. The APK itself is downloaded by native/AppUpdatePlugin.java (github.com release URLs only, package + newer-versionCode check) and installed through UpdateFileProvider. The workflow copies both Java files, registers the plugin, adds REQUEST_INSTALL_PACKAGES and the provider (res/xml/repopush_update_paths.xml), and passes VITE_RELEASE_REPOSITORY / VITE_APP_VERSION_CODE / VITE_APP_VERSION to the web build. Keep the tag number and the versionCode both equal to github.run_number.
- API budget: GitHub allows 5000 requests an hour per token. While a build runs, two pollers work (the per-repo build tracker and the open repo's watcher); both use src/lib/cadence.ts (1 s for the first 5 s, then 8 s). The watcher gets the tracker's run ids as `skip` in `runsOverview`, so a run the tracker follows is not verified or asked for its jobs a second time (about 3 instead of 5 requests per tick with one run).
- Lockfile: bun.lock is refreshed by the last step of android.yml (`bun install` runs there without --frozen-lockfile; if bun.lock changed, the step commits it back with `[skip ci]`). The repo has no Pages/deploy workflow: android.yml (manual `workflow_dispatch`) is the only one, so a push never starts a build.
